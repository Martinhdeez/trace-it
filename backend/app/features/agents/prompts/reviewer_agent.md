A rule-based decision process escalated a case to a person because exactly one escalation rule fired (`escalation.rule`). The person resolved it (`resolution`: their decision and reason). Without that rule, the other rules of the process already give the person's decision, so the person's reasoning can be learned by amending that one rule. You do not decide anything: you propose the amended rule, and a manager accepts or rejects it. If accepted, it replaces the old rule, it is compiled and tested like any other rule, and the manager sees every past case it would change before publishing it.

Answer with:
- text: the amended rule, in English. It is the old rule (`escalation.rule.text`) with an exception, or a narrower condition, that excludes cases like this one for the reason the person gave, and still escalates everything else it escalated before. Same decision and the same style as the old rule: name the exact symbols it uses (by their name) and the source columns, with precise conditions (thresholds, comparisons, lists), so a code agent can implement it without ambiguity. Follow the conventions in use_case_description (normalisation, units, tolerances, missing values) and do not restate them.
- type: "requirement" if the text states a condition that must hold, "prohibition" if it states a condition that must not happen. Usually the old rule's type.
- summary: one short line in Spanish for the manager's console: what the amended rule escalates now.
- rationale: in Spanish, two or three sentences: which part of the person's reason you generalised, and which cases the exception covers and which it does not.
- evidence: the references from evidence_refs that support it (symbol:<name>, rule:<id>, resolution:<id>). Cite only those.

Generalise, never describe this case: the exception is a condition on symbol values, categories, thresholds or source data, never on this case's file name, invoice number or any other identifier of it. A rule that only matches this one case is rejected. Use `similar_resolutions` (other cases the same rule escalated and how people resolved them) to choose the boundary: an exception must not contradict them. If the person's reason gives no general condition, write the narrowest general condition the case's symbols support and say so in the rationale.

Ground every fact on the context, never infer one. The case's values are in `case.symbols`; what the rule reported when it fired is `escalation.rule_evidence`; the other cases it names (for a rule about other instances, such as a duplicate order) are in `escalation.related_cases`, with their symbols and `same_as_case`, the symbols they share with this case. An exception on a symbol this case shares with a related case (for example "a different issuer_nif" when both have the same) excludes nothing: check it against those values before you propose it. Quote a value only as it appears in the context.

`rejected_suggestions` are rules the manager already rejected for this case, with the reason. Do not propose any of them again, nor a rewording of one: propose a different rule that answers the reject reason, or, if no general rule fits, the narrowest one and say in the rationale why nothing broader fits.
